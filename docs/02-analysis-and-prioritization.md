# 02 - Analysis and prioritization (MoSCoW)

## Functional requirements
| ID | Requirement | Prio. | Acceptance criterion | Verification |
|---|---|---|---|---|
| RF-01 | Load source data (Parquet from P1, or a direct load) into the warehouse | M | Then the source tables are available as `sources` in dbt | `dbt source freshness` and row count |
| RF-02 | Staging layer: rename, type and standardize columns | M | Then every source has a `stg_` model with standardized columns | dbt tests |
| RF-03 | Dimensional model: `dim_fundo`, `dim_data`, `fct_informe_diario`, `fct_captacao_mensal` | M | Then facts reference dimensions with no orphans | `relationships` test |
| RF-04 | History of registry changes with a snapshot (SCD type 2) | S | Given a registry change, then both versions exist with validity dates | `dbt snapshot` and query |
| RF-05 | Quality tests: unique, not_null, accepted_values, relationships and business rules | M | Then a test fails when invalid data is inserted on purpose | `dbt test` |
| RF-06 | Documentation and lineage generated by dbt | M | Then `dbt docs generate` shows the description and lineage of every mart | Review |
| RF-07 | API `GET /v1/fundos` with filters and pagination | M | Given a status filter, then only matching funds are returned, paginated | pytest + httpx |
| RF-08 | API `GET /v1/fundos/{cnpj}/serie` with a period | M | Then the ordered series is returned, or 404 if the CNPJ does not exist | pytest |
| RF-09 | API `GET /v1/rankings/captacao` per month | S | Then the top N of the month is returned | pytest |
| RF-10 | API key authentication and rate limiting | S | Without a key, then 401; above the limit, then 429 | pytest |
| RF-11 | Contract tests against the OpenAPI specification | S | Then no endpoint violates the contract | Schemathesis |

## Non-functional requirements, rules and constraints
| ID | Type | Description |
|---|---|---|
| RNF-01 | Performance | p95 below 300 ms on time-series queries (target) |
| RNF-02 | Reliability | `dbt build` fails CI if any test fails |
| RNF-03 | Security | Read-only API; key kept out of the repository; input validation with Pydantic |
| RNF-04 | Portability | Runs via Docker Compose; swappable warehouse adapter (local DuckDB, optional Athena) |
| RNF-05 | Maintainability | Models in staging → intermediate → marts layers, with a documented naming convention |
| RN-01 | Business rule | Net inflows = inflows − redemptions in the period |
| RN-02 | Business rule | Monetary values in BRL; dates in UTC-3 only at presentation time |
| RST-01 | Constraint | No recurring cost: local warehouse with DuckDB |

## Risks
| ID | Risk | Prob. | Impact | Mitigation |
|---|---|---|---|---|
| R-01 | Scope grows and the project is never finished | High | High | Strict MoSCoW; "Could" only after all "Must" items |
| R-03 | Lack of time | High | High | Incremental delivery: every epic produces something publishable |
| R-P3-01 | P1 dependency is late | — | — | Direct load script (RF-01) |
| R-P3-02 | A poorly defined dimensional model causes rework | — | — | Settle the grain and the diagram in task 3.1 before coding |
